URL Shortener (like bit.ly) — System Design Interview Practice

Design a URL shortening service that can handle millions of URLs and redirect requests efficiently. Work through the requirements, architecture trade-offs, and an interactive design review.

Interview prompt

Design a service that turns long URLs into compact links and resolves them with consistently low latency, even when traffic spikes.

  • Separate the link-creation path from the read-heavy redirect path.
  • Choose a short-code strategy and explain collision and capacity behavior.
  • Keep analytics, abuse checks, and operational work away from redirect latency.
  • Cover aliases, expiration, deletion, privacy, and cache invalidation.

Requirements and scale assumptions

  • Create a compact URL for a valid destination URL.
  • Redirect a short code to its current destination.
  • Support optional custom aliases and expiration dates.
  • Provide aggregate click analytics by time, referrer, device, and coarse location.
  • Let an authenticated owner update, disable, or delete a link.
  • Keep p95 redirect latency below 50 ms for cached links.
  • Remain highly available because every redirect is user-facing.
  • Make private or unlisted codes difficult to enumerate.
  • Allow creation to be slower than redirects while remaining reliable and idempotent.
  • Treat analytics as eventually consistent and never block a redirect on it.
  • 100 million new links per month.
  • 10 billion redirects per month with sharp viral peaks.
  • An average destination URL is about 120 bytes before metadata and indexes.
  • Read traffic is roughly 100 times heavier than write traffic.
  • Create traffic: ~40 req/s — Average write rate; quota and campaign bursts drive peak sizing.
  • Redirect traffic: ~3.9K req/s — Average reads; hot links can concentrate far more traffic on one code.
  • Code capacity: 62^7 = 3.5T — A seven-character Base62 namespace leaves ample room for growth.
  • Link storage: 50-100 GB/mo — Redirect rows stay small; raw click events usually dominate storage.

Data flow

  1. 1. Create a compact linkThe service validates the destination and policy, allocates a collision-free alias, and commits metadata before returning it.
  2. 2. Resolve a redirectEdge and link cache resolve the alias; a miss reads the link store, checks status and expiry, then returns the redirect with bounded latency.
  3. 3. Emit click telemetryThe redirect path appends a privacy-scoped click event asynchronously or through a buffered queue without waiting for analytics.
  4. 4. Aggregate analyticsWorkers deduplicate events, build time buckets, and expose a processing watermark for dashboards.
  5. 5. Expire, update, or deleteLifecycle workers and owner commands invalidate caches, tombstone aliases, and retain only policy-approved analytics and audit data.

Deep dives and trade-offs

  • Alias allocation and collision safetyFor the low-latency URL shortener, redirect resolution must be fast but must never bypass link status, expiry, or owner policy. Design for the failure case where hot aliases, cache staleness, destination abuse, and analytics bursts must not affect redirects or expose deleted links; keep retries, versions, and repair state explicit. Expose freshness, version, lineage, or audit metadata so operators and clients can distinguish current, pending, and degraded state.
  • Redirect cache and invalidationFor the low-latency URL shortener, redirect resolution must be fast but must never bypass link status, expiry, or owner policy. Keep this concern off unrelated request paths and partition it by the low-latency URL shortener access key. Expose freshness, version, lineage, or audit metadata so operators and clients can distinguish current, pending, and degraded state.

Expose freshness, version, lineage, or audit metadata so operators and clients can distinguish current, pending, and degraded state.
  • Random IDs versus sequential aliasesUse collision-safe random or centrally allocated IDs with a uniqueness constraint and idempotency. Sequential IDs are compact but reveal volume and become allocation hot spots without careful sharding.
  • Long cache TTL versus revocationCache active links with TTL and targeted invalidation on update, delete, or expiry; always enforce a bounded expiry policy. Long TTL improves hit rate but serves stale destinations after owner changes.
  • Synchronous click logging versus redirect latencyBuffer or enqueue click events and keep redirect success independent of analytics availability. Synchronous analytics adds tail latency and lets an analytics outage take down redirects.
